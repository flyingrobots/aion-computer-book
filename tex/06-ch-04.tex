\chapter{Double-Pushout Physics (DPO): The Rule of Rules}
\label{chap:dpo-physics}

There is a moment in every engineer's career when you stop asking: "What is the system?" and start asking:

\textbf{"How does the system change?"}

In debugging, in compilers, in distributed systems, in game engines, in databases, in AI training loops—you don't care about what \textit{is}. You care about what happened, what is happening, and what will happen if you touch this thing.

And sooner or later you run into a deeper question:

\textbf{"What does it even mean to change a system?"}

This is not a philosophical question. This is a practical one. When you mutate state, when you apply a function, when you compile code, when you propagate an event, when you update a scene graph—you are rewriting structure.

But rewriting complex, recursive structure turns out to be... hard.

Hard enough that most people never formalize it. Hard enough that systems break because of it. Hard enough that entire industries fall over because nobody asked what a "change" really is.

So this chapter introduces a tool with a reputation:

\textbf{Double-Pushout Rewriting (DPO)}

Or in the language of this book:

\textbf{The physics of Recursive Meta-Graphs. The Rule of Rules.}

\section{RMGs Come to Life Only When You Apply Rules}
\label{sec:rmg-life}

Recursive Meta-Graphs (RMGs), as we defined in \hyperref[chap:recursive-meta-graphs]{Chapter 3}, give us nested structure, wormholes, recursive universes, and compositional worlds.

But structure is inert. A graph without rules is just a map of a universe that does nothing. It is a frozen snapshot. To compute, you need transitions, transformations, laws, behavior, and semantics.

That is where DPO comes in. If RMG is the space, DPO is the physics. It defines the allowable motions within that space.

\section{The Wormhole Needs a Contract}
\label{sec:wormhole-contract}

From Chapter 3 you learned that edges are wormholes—structured tunnels with internal geometry. But wormholes can't just rewrite anything willy-nilly. They need interfaces. They need constraints.

They need a contract defining:
\begin{itemize}
    \item What they accept (input structure).
    \item What they preserve (invariant structure).
    \item What they output (new structure).
\end{itemize}

This is the precise conceptual role of the DPO rule's famous triplet:

\[ L \leftarrow K \rightarrow R \]

\begin{itemize}
    \item \textbf{L (Left-hand side)}: The pattern to match.
    \item \textbf{K (Interface)}: The context to preserve.
    \item \textbf{R (Right-hand side)}: The result of the rewrite.
\end{itemize}

Let's break it down in human terms.

\subsection{L — The Entrance to the Wormhole}
The pattern that must be present. The shape the wormhole expects to "match." If the graph doesn't contain $L$, the wormhole won't open. It is the \textit{precondition}.

\subsection{K — The Interface (The Mouth of the Wormhole)}
The structure that must remain identical on both sides. The part preserved across the rewrite. Think of $K$ as:
\begin{itemize}
    \item The shared boundary.
    \item The stable part.
    \item The invariant.
    \item The "shape" of the wormhole's throat.
    \item The identity that survives the transformation.
\end{itemize}
If the boundary doesn't match $K$, the rewrite is illegal.

\subsection{R — The Exit of the Wormhole}
The new structure that emerges. This replaces everything in $L$ that isn't in $K$ ($L \setminus K$) with the new structure in $R$. This is the "after" picture.

\section{"Typed Wormholes": The Intuition That Makes DPO Obvious}
\label{sec:typed-wormholes}

This is the cleanest way to think about DPO:

\textbf{A DPO rule is a typed wormhole.}

$L$ defines what the wormhole accepts. $K$ defines what must survive. $R$ defines what emerges.

If the RMG at runtime matches $L$, and the boundary matches $K$, the wormhole fires, and $R$ is installed. If not? The rule is illegal. The transition cannot happen.

This matches our engineering reality perfectly:
\begin{itemize}
    \item A compiler expects a valid AST (type $L$).
    \item An API expects a valid JSON payload (type $L$).
    \item A serialization step expects valid object structure.
    \item A database transaction expects valid schema constraints.
    \item An optimizer expects legal Intermediate Representation.
\end{itemize}

In every case, invalid input means no transition. Wormholes have types.

\section{DPO's "Dangling Condition," Explained Without Pain}
\label{sec:dangling-condition}

Mathematical DPO requires satisfying the "Dangling Condition." It sounds scary, but it simply means:
\begin{enumerate}
    \item No dangling edges.
    \item No illegal merges.
    \item No broken boundaries.
\end{enumerate}

In engineer language: \textbf{The wormhole cannot rip a hole in the universe.}

Everything it deletes must be entirely inside the scope of $L$. Everything it preserves must match the interface of $K$. Everything it outputs must respect the structure of $R$.

Replace "universe" with "RMG," and you get the idea. DPO rules are safe not because they are clever, but because they follow the simplest possible invariant:

\textbf{Rewrite only what you matched. Preserve what you promised.}

Everything else is implementation detail.

\section{Example: A Compiler Pass as a DPO Rule}
\label{sec:compiler-example}

Let's revisit our wormhole from Chapter 3:

\[ [\text{Source Code}] \xrightarrow{\text{Compiler Wormhole}} [\text{Machine Code}] \]

Inside that wormhole:
\begin{itemize}
    \item $L$ is the AST pattern to match (e.g., a specific loop construct).
    \item $K$ includes the parts of the program that remain intact (variable declarations, surrounding scope).
    \item $R$ is the optimized IR or generated machine code.
\end{itemize}

This explains why:
\begin{itemize}
    \item Invalid syntax kills the compile (pattern $L$ not found).
    \item Partial ASTs don't rewrite (interface mismatch).
    \item Optimizations must preserve meaning (the invariant in $K$).
    \item Symbol table entries survive.
    \item IR nodes mutate into assembly instructions.
\end{itemize}

The compiler is just a DPO rewrite engine in a fancy hat.

\begin{tcolorbox}[colback=gray!10, colframe=black, title=\textbf{📦 FOR THE SKEPTICAL ENGINEER™: "Bro Just Discovered Function Calls."}]
Let's get this objection out of the way. You might be thinking: \textit{"Isn't this just a function? $L \rightarrow R$?"}

Sort of. But also absolutely not.

\textbf{Function calls:}
\begin{itemize}
    \item Single input, single output.
    \item No internal rewrite semantics exposed to the system.
    \item No structured edges or nested universes.
    \item No "rule legality" checks beyond basic types.
\end{itemize}

\textbf{RMG + DPO edges:}
\begin{itemize}
    \item Accept complex subgraphs as input.
    \item Contain entire universes of computation.
    \item Can include closures, environments, and concurrency inside.
    \item Can be rewritten \textit{themselves}.
    \item Enforce safety via the dangling condition.
    \item Are part of a geometric space of possible rewrites.
\end{itemize}

A function call is a wormhole. An RMG edge is a civilization in a tunnel. We will revisit this fully in the C$\Omega$DEX.
\end{tcolorbox}
